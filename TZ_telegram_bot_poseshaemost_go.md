# ТЗ: Telegram-бот для учёта посещаемости учебной группы (Go)

## 1. Цель проекта

Бот предназначен для одной учебной группы. Каждый студент самостоятельно отмечает своё отсутствие на конкретном занятии, указывая причину (уважительная/неуважительная). Староста и его заместитель управляют расписанием и списком предметов, видят сводную статистику по группе.

В MVP поддерживается одна группа, но структура данных должна позволять добавить несколько групп в дальнейшем.

Интерфейс и сообщения бота — на русском языке.

## 2. Технологии и архитектура

Используй:

- Go;
- библиотеку для Telegram Bot API с поддержкой webhook, inline-кнопок (например `go-telegram-bot-api/telegram-bot-api` или `telebot`);
- встроенный `net/http` для приёма вебхука;
- SQLite;
- `database/sql` и драйвер `modernc.org/sqlite` (без cgo);
- SQL-миграции;
- Docker и Docker Compose.

Бот принимает обновления от Telegram через **webhook**, а не long polling. Приложение поднимает HTTP(S)-сервер, который слушает один эндпоинт для входящих апдейтов.

Используй совместимые стабильные версии зависимостей и зафиксируй их в `go.mod` и `go.sum`.

Реализуй монолитное приложение с одним работающим экземпляром. Раздели код на обработчики Telegram, бизнес-логику, работу с БД.

Стандартная структура Go-проекта:

- `cmd/bot` — точка входа;
- `internal/config` — конфигурация;
- `internal/telegram` — обработчики, кнопки и пошаговые диалоги;
- `internal/service` — бизнес-логика (проверка дедлайнов, права доступа, статистика);
- `internal/storage/sqlite` — SQL-запросы и работа с БД;
- `migrations` — миграции.

Используй явные SQL-запросы без ORM. Передавай `context.Context` в операции с БД и внешними API. Не усложняй проект микросервисами и лишними абстракциями.

## 3. Webhook

Требования к приёму обновлений через webhook:

- Приложение поднимает HTTP-сервер (`net/http`) и регистрирует единственный маршрут для апдейтов, путь которого включает секретный токен (например `/webhook/<WEBHOOK_SECRET_PATH>`), чтобы эндпоинт нельзя было угадать.
- Дополнительно проверяй заголовок `X-Telegram-Bot-Api-Secret-Token` (параметр `secret_token`, который передаётся при регистрации вебхука через `setWebhook`) и отклоняй запросы с неверным или отсутствующим значением (`403`).
- При старте приложение вызывает `setWebhook` с публичным HTTPS-URL, если он ещё не установлен или отличается от текущего (`getWebhookInfo` для проверки).
- TLS терминируется снаружи приложения — реверс-прокси (nginx/Caddy/Traefik) или облачный балансировщик; само приложение слушает HTTP на внутреннем порту. Если самоподписанный сертификат не используется, отдельная загрузка сертификата в Telegram не требуется.
- Обработчик вебхука:
  - быстро возвращает `200 OK` после приёма запроса;
  - тяжёлую обработку (бизнес-логику, запросы к БД) выполняет асинхронно либо синхронно, но без блокирующих долгих операций, чтобы Telegram не посчитал доставку неуспешной и не начал повторные попытки;
  - валидирует и безопасно парсит тело запроса (ограничение размера, `context.Context` с таймаутом).
- При `SIGINT`/`SIGTERM` сначала останавливается приём новых запросов (`http.Server.Shutdown` с таймаутом), затем закрывается БД — см. раздел «Надёжность и запуск».
- Для локальной разработки без публичного HTTPS-адреса в README опиши способ пробросить порт туннелем (например ngrok/cloudflared) и переключить `setWebhook` на этот адрес.
- Если переменная `WEBHOOK_URL` не задана или недоступна, приложение должно явно завершаться с понятным сообщением об ошибке конфигурации — тихого отката на long polling быть не должно.

Новые переменные окружения:

- `WEBHOOK_URL` — публичный базовый HTTPS-адрес (например `https://bot.example.com`);
- `WEBHOOK_PATH_SECRET` — случайная строка, используемая как часть пути эндпоинта;
- `WEBHOOK_SECRET_TOKEN` — значение для заголовка `X-Telegram-Bot-Api-Secret-Token`;
- `HTTP_LISTEN_ADDR`, по умолчанию `:8080` — внутренний адрес, который слушает приложение.

## 4. SQLite

База данных должна храниться в файле, путь к которому задаётся переменной окружения `DATABASE_PATH`.

Требования:

- включить внешние ключи (`PRAGMA foreign_keys = ON`);
- использовать WAL (`PRAGMA journal_mode = WAL`);
- настроить `busy_timeout`;
- применять транзакции для связанных изменений (например, создание отметки + проверка дедлайна);
- хранить файл БД в отдельном постоянном каталоге;
- в Docker подключать этот каталог через volume;
- учитывать ограничение SQLite на одновременную запись — для MVP допустимо ограничить пул одним соединением;
- настроить подключения так, чтобы PRAGMA-параметры применялись ко всем используемым соединениям;
- не удерживать транзакцию во время запроса к Telegram API.

Миграции должны выполняться до запуска обработчиков. При ошибке миграции приложение должно завершаться с понятным сообщением.

## 5. Роли и доступ

**Студент:**

- просматривает расписание и предметы;
- отмечает своё отсутствие на занятии с указанием причины (уваж/неуваж);
- отменяет или изменяет свою отметку до начала пары;
- просматривает свою историю отметок.

**Администратор — староста или заместитель:**

- управляет списком предметов;
- создаёт и редактирует расписание;
- управляет кодом приглашения и доступом студентов;
- просматривает сводную статистику по группе.

**Владелец:**

- обладает правами администратора;
- назначает и удаляет администраторов.

Telegram ID владельца задаётся через переменную окружения `OWNER_TELEGRAM_ID`.

Проверяй права при каждом административном действии, включая callback-запросы. Ограничения доступа должны действовать в бизнес-логике, а не только через скрытие кнопок.

Отметка студента не подтверждается старостой — модерация в MVP не требуется. Студент не может менять отметки других студентов.

## 6. Подключение

После `/start` бот показывает описание и предлагает ввести код приглашения.

При правильном коде пользователь подключается к группе и получает главное меню. Повторный `/start` не должен создавать дубликат пользователя.

Владелец должен иметь возможность выполнить первоначальную настройку группы и кода приглашения через бота. Администратор может заменить код; это не отключает уже подключённых студентов.

После отзыва доступа пользователь перестаёт видеть данные группы и не может ставить отметки.

## 7. Предметы и расписание

Администратор может создать, переименовать и архивировать предмет. Архивный предмет не отображается в списке для отметки отсутствия.

Ведение расписания реализуй через пошаговый диалог:

1. Выбор предмета.
2. Выбор дня недели (или конкретной даты, если расписание разовое).
3. Ввод номера пары и времени начала.
4. Просмотр карточки и подтверждение сохранения.

Обязательные поля: предмет, день/дата, номер пары, время начала.

В пошаговых диалогах должны быть кнопки «Назад» и «Отмена».

Храни состояния диалогов и черновики в SQLite, чтобы перезапуск не приводил к потере введённых данных. Одновременно у пользователя может быть один активный диалог редактирования.

Администратор может изменить любое поле занятия расписания или удалить его. Перед сохранением изменений показывай итоговую карточку.

## 8. Отметка отсутствия

Главное меню студента:

- «Меня не будет»;
- «Моя история»;
- «Настройки».

Сценарий «Меня не будет»:

1. Бот показывает список предметов на сегодня (или на ближайшие дни) согласно расписанию.
2. Студент выбирает предмет и пару.
3. Бот запрашивает причину: «Уважительная» или «Неуважительная» (для уважительной — необязательный комментарий).
4. Бот сохраняет отметку и отправляет подтверждение с текстом: «Отметка принята. Пожалуйста, не переноси эту Н в бумажный журнал».

**Дедлайн:** отметку можно поставить **только до начала пары** (по времени начала из расписания, в часовом поясе группы). После начала пары бот не показывает эту пару для отметки и отклоняет попытку создать/изменить/отменить отметку с понятным сообщением.

Отмена или изменение отметки доступны по тому же правилу — только до начала пары.

«Моя история» показывает список прошлых отметок студента (предмет, дата, причина).

Для длинных списков реализуй пагинацию. Если список пуст, показывай понятное сообщение.

Экранируй пользовательский текст при использовании форматирования Telegram и учитывай ограничения размера сообщений и callback-данных.

## 9. Сводная статистика для администратора

Команда/раздел `/group`:

- список отсутствующих на сегодня (или выбранную дату) по каждому предмету;
- разбивка по типу причины (уваж/неуваж);
- фильтр по предмету и по дате.

Реализация напоминаний и экспорта в Excel/CSV — вне рамок MVP, в этой версии не реализуются.

## 10. Команды

Реализуй:

- `/start` — подключение и главное меню;
- `/absent` — отметить отсутствие;
- `/mystats` — своя история отметок;
- `/settings` — настройки;
- `/help` — инструкция;
- `/admin` — панель администратора (предметы, расписание, код приглашения, сводная статистика; владельцу дополнительно — управление администраторами).

## 11. Данные и время

Храни:

- пользователей и роли;
- группу и код приглашения;
- предметы;
- расписание;
- отметки отсутствия (студент, предмет, дата/пара, причина, комментарий, время создания);
- историю административных изменений (создание/редактирование/удаление предметов и расписания);
- состояния диалогов и черновики.

Используй внешние ключи, ограничения уникальности и индексы для основных запросов.

Защити от дублирования:

- пользователей по Telegram ID;
- отметок — по паре студент–предмет–дата/пара (одна отметка на одно занятие).

Все даты храни в UTC в едином формате (Unix timestamp в секундах). В Go используй `time.Time`.

Ввод, отображение и проверку дедлайна («до начала пары») рассчитывай в часовом поясе группы `Europe/Minsk`. Явно показывай его в настройках и при вводе расписания. Обеспечь наличие базы часовых поясов в контейнере через `time/tzdata`.

## 12. Надёжность и запуск

- Храни токен и настройки в переменных окружения.
- Проверяй конфигурацию при запуске.
- Не записывай секреты в журналы.
- Используй `log/slog` для структурированных журналов.
- Логируй ошибки и административные изменения.
- При `SIGINT` и `SIGTERM` останавливай приём новых HTTP-запросов (`http.Server.Shutdown`), корректно завершай текущие операции и закрывай БД.
- Данные должны сохраняться после пересоздания контейнера.
- Используй многоэтапную сборку Docker-образа.

Переменные окружения:

- `TELEGRAM_BOT_TOKEN`;
- `OWNER_TELEGRAM_ID`;
- `DATABASE_PATH`;
- `GROUP_TIMEZONE`, по умолчанию `Europe/Minsk`;
- `LOG_LEVEL`;
- `WEBHOOK_URL`, `WEBHOOK_PATH_SECRET`, `WEBHOOK_SECRET_TOKEN`, `HTTP_LISTEN_ADDR` (см. раздел «Webhook»).

## 13. Результат работы

Создай:

1. Исходный код работающего приложения.
2. SQL-миграции.
3. `go.mod` и `go.sum`.
4. `Dockerfile` и `docker-compose.yml` с постоянным volume для SQLite.
5. `.env.example` без реальных секретов.
6. README с инструкциями локального запуска и запуска через Docker, настройки владельца и группы, миграций, резервного копирования и восстановления SQLite.
7. Тесты ключевой бизнес-логики и интеграционные тесты хранения данных на временной SQLite-базе.

Проверь:

- проверку дедлайна (до начала пары, с учётом часового пояса группы);
- создание, изменение и отмену отметки;
- уникальность отметки на пару студент–предмет–занятие;
- проверку прав (студент/администратор/владелец);
- восстановление диалогов после перезапуска.

В тестах используй управляемое время, чтобы не зависеть от реального времени выполнения.

Выполни `gofmt`, `go vet ./...`, `go test ./...` и сборку приложения. Если нет реального Telegram-токена, отдельно укажи, какие проверки взаимодействия с Telegram не удалось выполнить.

Не оставляй заглушек в основном функционале. Не добавляй функции за пределами MVP (напоминания и экспорт — не реализуются в этой версии). Рутинные технические решения принимай самостоятельно и кратко фиксируй в README.

## 14. Критерий готовности

Администратор может создать предмет и добавить занятие в расписание; студент видит занятие в списке и может отметить своё отсутствие с указанием причины до начала пары; после начала пары отметка недоступна; администратор видит корректную сводную статистику по группе.
